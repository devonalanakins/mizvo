## Browser-engine failure investigation

The initial V0.16 CI runs failed in Playwright 1.56.1's WebKit content process after 23 captured states; Chromium passed the complete journey. The failure screenshot then masked the original error because its page had crashed. The harness now retains the original error and partial completed checks before attempting optional screenshots, and labels each engine accurately.

Playwright maintainers describe a WebKit navigation/reload crash affecting 1.56 and identify 1.57 as containing the upstream fix: [Playwright issue 37766](https://github.com/microsoft/playwright/issues/37766). This is a relevant upstream lead, not proof of every local crash's root cause. The test-only Playwright dependency is deliberately pinned to **1.57.0**, with its matching lockfile/browser build, rather than suppressing WebKit, retrying until green, changing application permissions or removing checks. The final exact-source CI result determines whether the integrated journey is verified. No runtime dependency was added.

With the pinned runner updated, WebKit reached all 34 captured states but reported one same-origin read refused during the journey. [Playwright issue 43120](https://github.com/microsoft/playwright/issues/43120) documents WebKit's classification of requests started during document replacement as access-control page errors. The existing harness replaced documents without waiting for the previous application's asynchronous reads to settle. Its hard-navigation helper now waits for real network reads to settle before and after navigation, consistently in both engines. The original zero-page-error/CSP assertions remain unchanged; no message filter or exception was added. This is test synchronization, not a CORS permission change or a claim that every similar error is harmless.

## Migration, rollback and preservation

Migrations **001–008 remain byte-for-byte unchanged**, as does V0.15 `scripts/backup.ts`. Migration **009-release-review-audience.sql** adds one checked, non-null column with default `internal`. Existing review rows retain every original field and timestamp. Their historical role cannot be reliably reconstructed, so they remain private rather than deriving historical visibility from current membership. Legacy client feedback is still available internally; it is not automatically reclassified as client-visible.

New reviews capture `client` or `internal` from the authorized role at write. Changing roles later cannot publish old engineering comments. A client's acceptance is never engineering release approval.

A migration test builds an actual 001–008 database with a historical review, opens it with 009, verifies exact row preservation, integrity/foreign keys and refusal by older code. **Downgrading the migrated database in place is unsupported.** Restore a verified pre-upgrade snapshot into an isolated volume with the matching older artifact; preserve the failed newer database and receipts. Never delete the applied migration identity to force a downgrade. See [Release](RELEASE.md) and [Recovery](STAGING-REHEARSAL.md).
