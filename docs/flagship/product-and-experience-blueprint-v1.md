# MIZVO Flagship V1 — The Client Commission Operating System

**STATUS:** Proposed redesign and implementation contract, prepared November 5, 2026. No production deployment, signed client or approval from Jim/Cristy. Founder asked for a research-led AAA quality redesign, preserving existing code and history until the new experience is verified.

## Executive decision

Do **not** replace Mizvo with a general project management app; do **not** make The Current into the entire Mizvo business. Build one connected commission experience spanning public discovery, client decisions, internal engineering, live demonstration, evidence-driven release and client ownership. Use the simulated Jim/The Current engagement as test data and an engineering proof of the whole model. The Current stays in its own repository as the first bespoke delivery.

**Mizvo's first flagship product is the service and software-delivery experience. The Current is the first client build used to prove it.**

## 1. Products and boundaries

| Surface | Job to be done | Primary user | Owner / environment |
| --- | --- | --- | --- |
| Mizvo Discover | Understand capabilities, request help without technical vocabulary | Prospect | Mizvo-controlled public site |
| Mizvo Client Space | Understand goal, preview working results, make informed decisions, see support and ownership | Authorized customer | Mizvo portal; server-enforced client/project permissions |
| Mizvo Studio | Execute and verify complex engineering without losing the original client problem | Devon and later approved contributors | Mizvo private operations |
| The Current | Perform a story-led 90-day employee briefing experience | Authorized participants, Cristy, Jim | Separate client-bound deployment, data, keys, domain and repository |
| Public research / original components | Publish rights-cleared reusable engineering knowledge | Engineers/public | Correctly licensed independent source |

No universal admin that sees every organization's private content by default. Production deployments do not share their databases with Mizvo. A service credential is scoped, auditable and revocable.

## 2. The core UX invention hypothesis — Promise to Proof

One client relationship contains six always-visible questions, not six unrelated workspaces:

1. **Why?** What concrete problem must be solved and for whom?
2. **What?** What scope, option and financial commitment did the customer approve?
3. **What can I try?** Which exact preview is useful now?
4. **Is it real?** What source, tests, review and deployment actually passed? What has not?
5. **Who controls it?** Who owns domain, data, account, source and backups?
6. **What happens after?** How to get help, update, migrate, export or terminate support?

The signature interface component is a **Living Commission**: a plain-language evolving brief connected to real stage-specific decisions and verifiable delivery receipts. A prospective client must not be forced to understand GitHub, releases or cloud vendors.

This is differentiation as a hypothesis. Basecamp, Linear, Figma and Vercel already offer related capabilities; prove the integrated workflow is actually easier than combinations of existing tools before calling it unique.

## 3. The flagship client story — synthetic Jim

**Inquiry:** “Our first-90-day conversations need to feel personal and useful. The media/email process is confusing. We want an engaging fictional mystery too.” This is a simulated question, NOT a real quote or purchase.

**Discovery outcome:** Determine business owner and the employee/facilitator/sponsor relationship. Research the real pain: confusing file delivery, uncertain playback and accidental cross-audience leaks. The professional feedback process is separate from the optional story experience. Compare no-code/simple-email service, a mobile-friendly landing page and a dedicated application. Recommend the smallest effective alternative before upselling software.

**Commission direction:** If authorized by real buyer/contract later, build The Current as a separate standalone app: participant invitation, facilitator runner, sponsor/investigator fictional evidence, private production. Its 16-case campaign is one example, not the code framework. No copyrighted franchise material in public source or self-hostable demo.

**Success:** A nontechnical facilitator runs a full briefing from phone; participant understands the invitation and can see captions; sponsor sees only released fictional materials; client knows what the solution costs and who owns it; independent maintainer can restore an export.

## 4. User flows — every stage has artifact and decision

### A. Prospect / Discover
- Landing says what Mizvo does in one sentence. Show authentic open-source examples separately from commissioned work; don't invent paying customers.
- Main CTA “Describe what you want to make.” Progressive request form: What is hard now? Who is it for? What would improve? What is needed by when? Budget range optional. Consent and privacy first.
- After submission: confirmation of received request and realistic response expectations ONLY if an actual delivery service exists. No auto-promised calls or fake lead metrics.
- If out of scope, honest feasibility or referral, no manufactured contract.

### B. Founder's intake and feasibility
- New inquiry appears in a scoped Inbox with source/date, buyer identity unverified until confirmed, consent, risk level.
- Choose service-only / prototype / custom platform / not a fit, record rationale. Funding, rights and safety flags.
- Create discovery brief with observed problem, affected user, expected outcome, alternatives and assumptions. Ask client questions in human terms.
- Issue a proposed scope only after legal entity/contracting capability exists. Until then simulated items have explicit labels.

### C. Living Commission / Client Space
- Header: project name, one-sentence outcome, verified stage, health explanation based on actual blockers (never a fabricated percent), contact and ownership.
- Home is **one meaningful action**. E.g. “Review how a briefing starts on a phone.” Adjacent “Why this matters” and “What happens if you approve.”
- Tabs/secondary: Overview, Experience, Decisions, Delivery, Support & Ownership. Developer vocabulary hidden by default; advanced inspector accessible on demand.
- Versions pinned and approval data immutable: exact preview+revision must not silently change after approval.
- Client can ask for changes with feedback anchored to a screen/moment. This creates a scoped request, never silently rewrites a commitment.
- Separate client-signoff for requirements/design/content, engineering verification, legal/contractual acceptance and production deployment. None implies another.

### D. Studio / Engineer experience
- A cinematic editorial three-region workspace: slim left rail; center Living Commission and work; contextual right rail showing the customer's decision, source evidence, risks and next action.
- Project room conversation and notes, verified milestones, versioned proposals, scoped invitations, actual tasks and dependencies, Git source/CI, release and handoff.
- **Proofline** navigation along Need → Decision → Preview → Verification → Live → Ownership. Each node shows factual status, source reference and blockers.
- Engineer can inspect code and evidence but client view receives only an explicitly approved projection.
- Roles initially Founder + Client; later invited Contributor. Future AI can suggest drafts and test cases but cannot approve on behalf of humans or access clients outside grants.

### E. Preview and demo
- Real authenticated preview bound to commit/version/environment. Show accessibility, mobile, and error/recovery state.
- Safe synthetic demonstration per client rights; private media only available through authorized object access.
- Preview link protects source and customer data; expiry and revocation tested.
- “Looks approved” is not “works correctly”; record independent functional and security evidence.

### F. Release and client-owned hosting
- Default proposed service: customer-owned hosting, Mizvo-operated with least privilege. Alternatives: fully self-hosted, Mizvo-hosted only when verified.
- Release Passport: version commit, dependency inventory, licenses, actual build artifact hashes, deployment target and actual observed app version; accessible QA and recovery evidence.
- Customer receives documented admin role, billing owner, secure backup/export, release notes, support contact, clear start/end support scope and exit steps.
- Deploy with explicit approval, never conflate CI pass with LIVE.

### G. Continuous care / offboarding
- Service status, next maintenance, support requests/response windows and change orders (when contractually defined).
- “Leave anytime” only if independent export/restore is proved, not by marketing claim. Client domain and production data remain in client control.
- Incident owner, escalation and customer notification defined before a support SLA is sold.

## 5. Mizvo flagship design system — EVOLUTION of prior founder-approved design

Protect identity anchors: graphite #0B0D11, deep layers #13161B/#1D2026, warm ivory #F1ECE5, copper #D3A379, sophisticated architectural geometry, strong editorial hierarchy. Replace the flat text-logo treatment with a distinct vector emblem and letterform exploration; the final mark needs founder selection, name/right clearance and responsive checks.

**Visual statement:** Architectural cinematic editorialism, made tactile and human. The *structure* appears complex, the *action* feels simple. Signature motif: slender copper curves/bridge structures that literally connect the six Promise-to-Proof moments; perspective planes subtly shift as context changes. No generic sci-fi nebula or opaque glass dashboard.

Typography: distinctive open-license editorial display serif for sparse heroes, clear compact sans for controls, optional monospace for evidentiary SHA/CI. Avoid body copy below 14px. Build all content as semantic DOM, not rasterized screenshot art.

Color system: dark public/Studio surfaces with warm ivory text, copper as editorial focus only, contextual neutral/success/error statuses with semantic labels; lighter Client Space surfaces where decision readability improves. Verify actual color pair contrast against WCAG 2.2 AA. Token values remain proposal, not finished visual QA.

Motion: high-framerate but gentle scene transition with reduced-motion parity. Use optical-depth layers to distinguish context; smooth 160–300ms motion, never require gesture/hover for critical actions. Fail-safe at 320px through 1920px.

Content-first polish: accurate copy, real empty/loading/denied states, responsive tables, explicit timestamps and permission-specific blank states. The premium feeling should survive disabled animation and a slow 4G phone.

### Screen-level visual storyboard

1. **Discover hero:** full editorial headline “Make the improbable useful.” Original copper architecture spanning dark graphite. Compact differentiator: “Complex engineering. Human-scale experiences.” Primary CTA “Start with your problem”; secondary CTA “See how we work.”
2. **Inquiry:** warm quiet 3-question conversational intake with optional attachments; never collect confidential or protected data in an unsecured public form.
3. **Proposal review:** two or three plain alternatives showing outcomes, exclusions, total fee range (only after real estimation), owned infrastructure, maintenance, timeline and one clear choice.
4. **Client home:** human headline “Here's what matters now”; one live preview and one pending decision. Small side column for delivery status and owner contact.
5. **Experience review:** large real prototype with a phone/desktop switcher; anchored feedback; explicit version and audience; “approve this version” is clear and revocable only through controlled revision.
6. **Studio project:** three-region dark interface; central client promise and current task; right inspector traces customer need → issue → source → tests → evidence → demo, with real actor/version.
7. **Release gate:** checkable release receipt with real provenance and blockers; no simulated green shields presented as passed verification.
8. **Ownership and care:** calm customer handoff card showing domain, infrastructure owner, backups/restore evidence, source license, support scope and export.

## 6. Proposed information architecture

Discover: Home, Services, Process, Authentic Work, Open Source, About, Inquiry.

Authenticated Studio: Home/Decisions, Inbox/Discovery, Clients, Commissions/Rooms, Workbench, Proofline/Delivery, People (later), Operations and Security.

Client Space: Home, Experience, Decisions, Delivery, Care. Project-specific views. No generic analytics full of empty graphs. Advanced evidence drawer on demand.

Engineering entities (adapt existing and extend rather than replace): inquiry, customer organization, contact/authority, engagement, commission, living brief revision, need/outcome, scope alternative, deliverable, decision request, approval, project/task/milestone, source ref, build evidence, preview, release candidate, environment, deployment receipt, hosting ownership passport, support ticket/response, exit/export event and audit.

## 7. Engineering architecture and non-negotiable invariants

- Current implemented Mizvo runtime is Node 24/SQLite, not cloud-deployed or verified on Cloudflare Workers. Preserve functioning source, migrations, auth, authorization, projects, milestone and client decision code. Additive migrations only.
- Before changing UI, extract stable human-readable domain workflows and route contracts from existing server. The three-region design can be reworked progressively behind feature flags without new application rewrite.
- No cross-organization client visibility; no cross-project membership leakage. Each record/asset/action authorized at server and independently filtered for customer projection. Revocation applies to open clients; optimistic updates cannot bypass state gates.
- Contract/deliverable/payment flows are future modules; don't pretend to sign or collect money on a mock.
- Dedicated per-customer deployment with scoped service credentials; client account/domain/data owned by client by default. Source license and commissioned IP decided explicitly.
- Portable self-hosting not a claim until second-environment tested restore and export works. Keep Cloudflare D1 adapter as proposed, not existing.
- Evidence integrity: CI green != verified artifact != deployed != observed production. Each has a separate event/receipt with actor and environment.
- Capture no actual client employee feedback or patient information in the synthetic first flagship scenario.
- Accessibility: WCAG 2.2 AA goal; browser + screen-reader + no-coaching nontechnical usability test. Visual excellence and usability both required.

## 8. Acceptance gates — the work is staged, not imaginary

**R0 Preserve & inspect (actual next action):** Snapshot PR #2 head, diff, current executable structure, tests and exact baseline screenshot. Commit proposed design to *separate branch* based on main, leaving PR #2 and main untouched. Capture baseline failure and feature inventory. Gate: all current records, SHA links and historical design files remain retrievable.

**R1 Human journey prototype (in design branch):** an original interactive no-backend demo of Discover → fictional inquiry → client decision → studio proofline → handoff. Every screen labels synthetic data and never claims actual integration. Run responsive screenshots and 2 simple no-coaching comprehension trials. Gate: correct task completion, no horizontal overflow, no dead primary CTA.

**R2 Real engine integration (after review):** rebase/stack against implemented PR #2 after deciding its merge timing. Extend only needed domain types and endpoints, real auth/roles, persistent Living Brief and decision, transparent client projection and version-bound preview. No rewrite of tested code. Gate: strict typecheck, test suite, negative auth cases, migration preservation, browser mobile/accessibility.

**R3 The Current first commission:** define a synthetic organization/client and one original narrative microcase. The Current stays in its own repo and own backend. Link only milestones/source/release to Mizvo via narrow API, never share database. Gate: user no-coaching rehearsal, role isolation, direct-media denial, backup/restore, explicit manual fictional reveal.

**R4 Staging and release:** exact source/build artifact/deploy attestation, staging auth and availability, customer cloud ownership handoff, human review and real client contract/privacy/content gates. Real external launch requires separate approval. No live app claimed until observed.

**R5 Support/scale:** measure actual operation; only introduce payments, advanced finance, AI assistants, real-time meetings, multi-tenant SaaS, automated emails, additional compliance modules where justified and staffed.

## 9. MVP product cuts

BUILD: clear public inquiry, human-readable Living Brief, existing scoped Room, one visible client decision tied to exact version, verified source preview reference, support request, clear ownership passport draft.

DO NOT BUILD NOW: universal CRM, accounting suite, automatic contract signatures, payroll, 24/7 service promise, cross-client analytics, user monitoring, new video calling platform, bespoke AI model, generic training LMS, simulation of hundreds of customers, hypothetical employee performance scoring.
